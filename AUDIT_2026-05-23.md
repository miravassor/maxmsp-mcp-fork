## Bugs Found: 7

### BUG 1 — `list_open_patchers`: `is_current` always false

**Severity**: MEDIUM
**Reproduction**: Call `switch_to_patcher("sandbox")` (returns success), then `list_open_patchers()` — all entries show `is_current: false`.

**Root cause** (`max_mcp.js:867`):
```javascript
is_current: (p === current_patcher)
```
Uses JavaScript object identity (`===`). The patcher reference from `w.assoc` in the window chain is a different wrapper object than the one stored by `switch_to_patcher`, even when they represent the same patcher.

**API check**: Official docs say `wind.assoc` returns a `Patcher` (read-only). **No guarantee of object identity** across calls — the docs don't promise `===` equality for the same underlying patcher.

**Fix**: Compare by name + filepath:
```javascript
is_current: (p.name === current_patcher.name && p.filepath === current_patcher.filepath)
```

### BUG 2 — `get_objects_in_patch`: `patching_rect` format inconsistency

**Severity**: HIGH
**Reproduction**: In the same patcher, objects loaded from disk return `[left, top, right, bottom]` while objects freshly created via `add_max_object` return `[left, top, width, height]`:

| Object | patching_rect | Format | Decoded size |
|--------|---------------|--------|-------------|
| plugin~ (loaded) | [48, 34, 101, 54] | l,t,r,b | 53 x 20 |
| toggle (loaded) | [275, 498, 299, 522] | l,t,r,b | 24 x 24 |
| button (created) | [50, 572, 24, 24] | l,t,w,h | 24 x 24 |
| + 1. (created) | [50, 640, 33, 20] | l,t,w,h | 33 x 20 |

**Root cause** (`max_mcp.js:1198`): Uses `obj.rect` directly and labels it `patching_rect`.

**API check**: Official Maxobj docs state `rect` is `"(left, top, right, bottom)"` — explicitly. No mention of format differences between loaded and newly created objects. The inconsistency for freshly-created objects is a **Max API quirk** not documented anywhere.

Meanwhile, `obj.getboxattr("patching_rect")` (used in v8's `get_object_attributes`) consistently returns `[left, top, width, height]` — this is Max's internal storage format.

So there are two representations:
- `obj.rect` → [l,t,r,b] per docs, but unreliable for newly-created objects
- `obj.getboxattr("patching_rect")` → [l,t,w,h] consistently

**Fix (option A)**: Replace `obj.rect` with `obj.getboxattr("patching_rect")` in `collect_objects()` for consistent [l,t,w,h] output. However, `getboxattr` is only available in v8, not classic js. Route the entire collection through v8.

**Fix (option B)**: Normalize in classic js by detecting impossible [l,t,r,b] values (where `rect[2] < rect[0]`), treating those as [l,t,w,h] and converting:
```javascript
var r = obj.rect;
if (r[2] < r[0]) {  // width < left → must be [l,t,w,h]
    r = [r[0], r[1], r[0] + r[2], r[1] + r[3]];
}
```

**Fix (option C)**: Always convert to [l,t,w,h] (the format consumers expect from `patching_rect`):
```javascript
var r = obj.rect;
if (r[2] > r[0] && r[2] > 100) {  // likely [l,t,r,b]
    r = [r[0], r[1], r[2] - r[0], r[3] - r[1]];
}
```

### BUG 3 — `get_avoid_rect_position`: no output for empty patcher

**Severity**: MEDIUM
**Reproduction**: Enter newly created empty subpatcher → `get_avoid_rect_position()` → no output.

**Root cause** (`max_mcp.js:1218-1237`): `var l, t, r, b;` remain `undefined` when 0 objects. `JSON.stringify([undefined, ...])` → `[null,null,null,null]`. Python server cannot interpret null coordinates.

**API check**: `patcher.apply(fn)` — "For all objects in a patcher, call a given function." Empty patcher = callback never fires. This is expected behavior per docs. The bug is in the MCP code not handling the empty case.

**Fix**:
```javascript
if (l === undefined) {
    avoid_rect = [0, 0, 0, 0];
}
```

### BUG 4 — `set_presentation_mode`: view changes but `openinpresentation` not updated

**Severity**: LOW
**Reproduction**: `set_presentation_mode(1)` returns success. `get_patcher_context()` → `openinpresentation: 0`.

**Root cause** (`max_mcp.js:966`):
```javascript
tp.message("presentation", mode ? 1 : 0);
```
Sends thispatcher message which changes the **view** but not the **attribute**.

**API check**: Official thispatcher docs: `presentation` — *"will cause the patcher to enter or exit presentation mode"*. This is described as a view-mode toggle, not an attribute write. `openinpresentation` is **not documented** in the Patcher API at all — it's an undocumented patcher attribute that stores the saved default.

**Conclusion**: Behavior matches the docs. The thispatcher `presentation` message correctly toggles the view. The MCP's `get_patcher_context` reads the saved attribute, not the live view state. Both work as documented; the MCP just doesn't sync them.

**Fix**: Add after the thispatcher message:
```javascript
current_patcher.setattr("openinpresentation", mode ? 1 : 0);
```

### BUG 5 — `dirty` always false after programmatic changes

**Severity**: LOW
**Reproduction**: Add objects, modify parameters, connect/disconnect — `get_patcher_context()` → `dirty: false`.

**Root cause** (`max_mcp.js:1064`):
```javascript
if (current_patcher.wind) dirty = current_patcher.wind.dirty ? true : false;
```

**API check**: Official Wind docs: `dirty` — *"Whether the window's contents have been modified."* Does NOT specify whether programmatic changes via JS API set the flag.

Official thispatcher docs provide explicit messages:
- `dirty` — *"sets the patch's dirty bit in the window"*
- `clean` — *"resets the patch's dirty bit in the window"*

**Conclusion**: The docs provide the `thispatcher.dirty` message precisely for this use case. Programmatic changes don't automatically set `wind.dirty` — you must explicitly send the `dirty` message.

**Fix**: After any programmatic modification, send:
```javascript
tp.message("dirty");
```
Or, more precisely, call this at the end of any write operation in `max_mcp.js`.

### BUG 6 — `object_count` off-by-1 vs `get_objects_in_patch`

**Severity**: LOW
**Reproduction**: `get_patcher_context` reports 14, `get_objects_in_patch` returns 13 boxes.

**Root cause**:
- `get_patcher_context` uses `current_patcher.count` (line 1076)
- `get_objects_in_patch` filters out `maxmcpid_*` objects (line 1177-1178)
- The hidden `maxmcpid_save_tmp` thispatcher (created by save/presentation tools) causes the +1

**API check**: Official Patcher docs: `count` — *"Number of objects in the patcher"*. Does NOT specify whether it includes hidden or system objects.

**Conclusion**: `patcher.count` counts ALL objects including hidden ones. The MCP creates a hidden thispatcher but doesn't account for it in `object_count`. This is an MCP inconsistency, not an API issue.

**Fix**: Either filter in `get_patcher_context`:
```javascript
var hidden_count = 0;
current_patcher.apply(function(obj) {
    if (obj.varname && String(obj.varname).substring(0, 8) === "maxmcpid") hidden_count++;
});
object_count: current_patcher.count - hidden_count
```
Or document the discrepancy.

### BUG 7 — `set_parameter_property` on non-parameter objects: soft failure

**Severity**: LOW
**Reproduction**: `set_parameter_property("obj-0", "_parameter_shortname", ["Test"])` on plugin~ (parameter_enable=0). setattr doesn't throw, readback returns null, `success: false`.

**Root cause**: The tool proceeds with setattr without checking `parameter_enable` first.

**API check**: Not an API issue — pure MCP validation gap.

**Fix** (in `max_mcp_v8_add_on.js`, `set_parameter_property_v8`):
```javascript
var pe = obj.getattr("parameter_enable");
if (!pe) {
    // return error: "Object does not have parameter_enable=1"
}
```

## API Reference Summary

All bug analysis cross-referenced against these official doc pages:

| Page | URL |
|------|-----|
| Maxobj | https://docs.cycling74.com/apiref/js/maxobj/ |
| Patcher | https://docs.cycling74.com/apiref/js/patcher/ |
| Wind | https://docs.cycling74.com/apiref/js/wind/ |
| thispatcher | https://docs.cycling74.com/reference/thispatcher |

Key confirmed API facts:
- `obj.rect` is documented as `[left, top, right, bottom]` — no exceptions mentioned
- `wind.dirty` tracks "whether the window's contents have been modified" — no detail on programmatic changes
- `thispatcher.dirty` / `thispatcher.clean` are the official way to set/reset the dirty bit
- `thispatcher.presentation` toggles the view — docs say nothing about updating attributes
- `patcher.count` is "Number of objects in the patcher" — no exclusion rules specified
- `patcher.openinpresentation` is **not documented** at all
- `wind.assoc` returns a `Patcher` — no identity guarantees across calls
