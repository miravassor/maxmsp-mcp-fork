## TIER 1 — HIGH Severity (6 findings)

### H1. Signal safety gain check for `*~` likely never fires (`maxclass` mismatch)

**Files**: `max_mcp.js:477,1592` + `max_mcp_v8_add_on.js:294`

All three signal safety paths check `mc === "*~"`, but strong evidence indicates `obj.maxclass` returns `"times~"` (the internal class name). The v8 file's own `complete_encapsulate` comment (line 449) explicitly states maxclass returns internal names like `"greaterthan~"` and `"trigger"`, and the `internal_to_user_class` map (line 364) maps `"times~" -> "*~"`. If confirmed, the HIGH_GAIN warning for `*~` objects has never fired.

**Needs empirical verification against running Max.** If `obj.maxclass` returns `"times~"`, every `mc === "*~"` check in signal safety is dead code.

**Fix**: Check both names: `mc === "*~" || mc === "times~"`, or normalize via the existing `internal_to_user_class` map.

---

### H2. Subpatcher `*~`/`comb~` objects silently skipped in v8 gain/feedback check

**File**: `max_mcp_v8_add_on.js:285-288`

`collect_signals_recursive` (max_mcp.js) produces path-prefixed varnames like `"delay_fx > gain_fb"` in `objects_to_check`. The v8 side calls `current_patcher.getnamed("delay_fx > gain_fb")` which fails — `getnamed` only searches by bare varname, not path. The `if (!obj) continue` on line 288 silently skips every subpatcher object.

Combined with H1, the gain/feedback value check is completely non-functional: root-level objects fail the name match (H1), subpatcher objects fail the lookup (H2). Only `comb~` at root level is checked.

**Fix**: Strip the path prefix before lookup and navigate to the correct subpatcher, OR have max_mcp.js pass `boxtext` values alongside `objects_to_check` so v8 doesn't need to look up objects at all.

---

### H3. `server.py` lifespan `else` branch: unbound `maxmsp` + missing `yield`

**File**: `server.py:104-107`

If `server_lifespan` is entered when `io_server_started` is already `True`, the `else` branch references local `maxmsp` (only defined in the `if` branch) -> `NameError`. It also never calls `yield`, violating the `@asynccontextmanager` contract, which would cause FastMCP to hang.

In practice FastMCP only enters the lifespan once, so this never triggers. But the code is broken if reuse ever happens.

**Fix**: Remove the `else` branch entirely (or store `maxmsp` at module scope and add `yield`).

---

### H4. `start_server` swallows connection failure — server runs "connected" on dead socket

**File**: `server.py:64-76`

`start_server` catches `OSError` (line 75) but doesn't re-raise. `server_lifespan` then sets `io_server_started = True` and yields the dead connection. All subsequent tool calls fail with opaque errors when they try to emit on a disconnected socket.

**Fix**: Remove the try/except in `start_server` and let the lifespan's own exception handler deal with it.

---

### H5. Node bridge: connection handler lost after port change

**File**: `max_mcp_node.js:38-44, 63-66`

When `io` is reassigned to a new `Server` after a port change, the `io.of(NAMESPACE).on("connection", ...)` handler (line 46) is attached to the old (closed) server. The new server accepts connections but has zero event handlers — all requests are silently dropped.

**Fix**: Extract connection handler setup into a function and call it after every `new Server(...)`.

---

### H6. Node bridge: dual port-change handlers race, leak server instances

**File**: `max_mcp_node.js:33-44, 58-69`

Both `Max.addHandler("port", ...)` and `socket.on("port", ...)` can close and recreate the server. If both fire simultaneously, two servers are created and one leaks with no reference.

**Fix**: Remove the `socket.on("port", ...)` handler (unused by server.py) or consolidate into a single guarded function.

## TIER 2 — MEDIUM Severity (12 findings)

### M1. `asyncio.get_event_loop()` deprecated — breaks Python 3.14

**File**: `server.py:49`

`asyncio.get_event_loop().create_future()` is deprecated. Currently works inside async functions but will raise `RuntimeError` in Python 3.14.

**Fix**: `asyncio.get_running_loop().create_future()`

---

### M2. `TimeoutError` raised as bare exception instead of structured error

**File**: `server.py:60`

When Max doesn't respond, tools raise `TimeoutError` producing a Python traceback instead of `{"success": false, "error": "..."}`.

**Fix**: Return a structured error from `send_request` instead of raising.

---

### M3. No `maxmsp is None` check in any tool function

**File**: `server.py` (every tool, ~line 401, 431, 456, etc.)

If the connection failed silently (per H4), `ctx.request_context.lifespan_context.get("maxmsp")` returns `None`. The next call crashes with `AttributeError: 'NoneType' object has no attribute 'send_request'`.

**Fix**: Add a helper that returns `{"success": false, "error": "Not connected to Max"}`.

---

### M4. `assert` used for input validation

**File**: `server.py:402`

`assert len(position) == 2` is stripped with `python -O`. Use a proper validation check with a structured error return.

---

### M5. 11 dispatcher cases silently drop requests when fields are missing

**File**: `max_mcp.js` — cases at lines 155-159, 195-198, 200-203, 205-208, 210-213, 215-218, 220-223, 225-228, 230-233, 284-287, 310-313

When required fields are missing, these cases `break` without sending a response. The Python server's future times out after 2-5 seconds with a confusing timeout error instead of a clear missing-field error.

**Fix**: Add `else` branches that send structured error responses.

---

### M6. `encapsulate` sends large payloads to v8 without chunking

**File**: `max_mcp.js:1977`

`outlet(2, "complete_encapsulate", JSON.stringify(encap_data))` can exceed Max's ~16KB symbol limit for large encapsulations (50+ objects). `send_chunked_to_v8` exists for this purpose but isn't used here. Same issue on line 1755 for `complete_signal_safety`.

---

### M7. `encapsulate` always creates `inlet`/`outlet` — never `inlet~`/`outlet~`

**File**: `max_mcp.js:1936-1946`

When encapsulating signal objects with signal connections, the subpatcher gets message-type inlets/outlets instead of signal inlets/outlets, breaking the audio chain.

**Fix**: Check whether external connections involve signal objects (`maxclass` ending in `~`) and create `inlet~`/`outlet~` accordingly.

---

### M8. `recreate_with_args` missing jbogus check

**File**: `max_mcp.js:1461-1472`

`add_object` checks for `new_obj.maxclass === "jbogus"` but `recreate_with_args` does not. If the recreation fails, the old object is already removed and a broken placeholder is left. `success: true` is returned.

---

### M9. `recreate_with_args` missing `live.comment` in type list

**File**: `max_mcp.js:1476`

`add_object` handles `live.comment` text setting but `recreate_with_args` doesn't. Recreating a `live.comment` loses its text.

**Fix**: Add `|| obj_type == "live.comment"` to the check.

---

### M10. `_on_response` crashes on non-dict data

**File**: `server.py:40-44`

If Max sends a non-dict response (e.g., `null` from a parse failure in the node bridge), `data.get("request_id")` raises `AttributeError`, crashing the handler and orphaning all pending futures.

**Fix**: Add `if not isinstance(data, dict): logging.error(...); return`.

---

### M11. Node bridge emits `null` to Python on JSON parse failure

**File**: `max_mcp_node.js:28-30`

If `safe_parse_json` returns `null`, the code emits `null` to Python, which triggers M10.

**Fix**: Add `if (!data) return;` after parse.

---

### M12. Node bridge: invalid port still kills the old server

**File**: `max_mcp_node.js:35-43`

If port validation fails (e.g., `msg = -1`), the `io.close()` and `new Server()` calls still execute outside the `if` block, performing an unnecessary restart on the old port.

## Comparison with previous audit (2026-05-23)

The 2026-05-23 audit tested all 38 tools **empirically** against a live Max instance and found 7 bugs (all fixed in iterations 3-7). This 2026-05-25 audit is a **static code review** covering correctness, edge cases, and cross-component interactions that empirical testing missed.

Key differences:
- Previous audit verified tool I/O behavior; this audit found structural bugs in error handling, signal safety, and cross-engine communication
- H1+H2 (signal safety completely non-functional for `*~`) was not caught empirically because the previous audit's signal safety test used a "safe" patch with no high-gain objects
- M5 (silent request drops) was not caught because empirical testing always provided valid fields
- H3-H6 (server lifecycle bugs) are infrastructure issues that don't surface in normal single-session testing
